## Замечания

### 1. Порядок обхода в `has_road_access` начинается с самых дальних клеток (расстояние 3 вместо 1)
- Файл: `scripts/grid/city_grid.gd:151-157`
- Серьёзность: мелочь
- Суть: цикл `for dy in range(-ROAD_ACCESS_RANGE, ROAD_ACCESS_RANGE + 1)` начинает проверку с `dy = -3` (северный край ромба на расстоянии 3 клеток), и только к середине цикла доходит до соседних клеток на расстоянии 1. Кроме того, в фазе 4 при постройке здания (`BuildingInstance.orientation`) потребуется знать не только факт наличия дороги в радиусе 3, но и **направление к ближайшей дороге**, чтобы повернуть дом к ней лицом (`ARCHITECTURE.md:78`).
- Предложение:
  - В фазе 4 добавить функцию `find_nearest_road_dir(cell: Vector2i) -> int` (возвращает `0..3` для N/E/S/W или `-1`, если дороги нет), перебирающую манхэттенские кольца от `dist = 1` до `ROAD_ACCESS_RANGE`.
  - Тогда `has_road_access(cell)` можно выразить через `return find_nearest_road_dir(cell) != -1` (или оставить текущий цикл для пустых мест, но при наличии дороги рядом выход по `return true` сработает за 1–4 проверки вместо 10–15).

### 2. Перекраска `ZoneVisualizer` при несвязанных с дорогами изменениях и при длинной «Г»-дороге
- Файл: `scripts/grid/zone_visualizer.gd:48-64`
- Серьёзность: мелочь
- Суть:
  1. **Края карты (вопрос 2 из задания):** расчёт `area.expand(cell)` → `area.grow(ROAD_ACCESS_RANGE)` → `clamp_to_bounds(area.position)` / `clamp_to_bounds(area.end)` и цикл до `bottom_right + 1` **полностью корректен**. `Rect2i.expand` и `grow` дают включительную правую/нижнюю границу в `area.end`, а `clamp_to_bounds` гарантирует, что индексы никогда не выйдут за `0..size - 1` на краях и углах карты.
  2. **Длинная операция через карту:** если провести дорогу «Г» от `(0, 0)` до `(63, 63)` (127 клеток) или в фазе 4 за один тик вырастут 2 дома в разных углах карты `(2, 2)` и `(60, 60)`, охватывающий `Rect2i` накроет всю карту `64×64 = 4 096` клеток.
  3. **Производительность (вопрос 3 из задания):** на карте `64×64` обход `Rect2i` без аллокаций и дубликатов (максимум `4 096` вызовов `_update_cell`, причём `has_road_access` вызывается только для клеток, где `zone_type != Zone.NONE`) работает **быстрее**, чем сбор ромбов вокруг каждой изменённой клетки через `Dictionary[Vector2i, bool]` (на 127 клетках дороги это дало бы `127 × 49 = 6 223` хэш-операций со словарём). Поэтому для `64×64` текущее решение с `Rect2i` оптимально по соотношению простоты и скорости.
- Предложение:
  - Для `64×64` в MVP можно оставить как есть.
  - Если в фазе 4 `growth.gd` будет эмитить `Events.cells_changed` при появлении нескольких зданий в разных частях карты (или при переходе к `256×256`), то при `cells.size() <= 8` выгоднее обходить отдельный `Rect2i(cell, Vector2i.ZERO).grow(ROAD_ACCESS_RANGE)` вокруг каждой клетки из `cells`, чем один общий `Rect2i` на всю карту.

### 3. Поведение `ZoneVisualizer` под построенными зданиями в фазе 4
- Файл: `scripts/grid/zone_visualizer.gd:66-73`, `scripts/grid/city_grid.gd:126-127`
- Серьёзность: мелочь
- Суть: в фазе 4 при постройке здания на клетке `tile_type[i]` станет `Tile.BUILDING`, а `zone[i]` останется `RESIDENTIAL`/`COMMERCIAL`/`INDUSTRIAL` (так как снос здания по `ARCHITECTURE.md:70` не должен стирать зону). Сейчас `_update_cell` смотрит только на `grid.get_zone(cell)` — значит, плашка зоны продолжит рисоваться под зданием (и тускнеть, если у здания пропадёт дорога). Кроме того, в `get_zone(cell)` нет комментария о том, что `cell` должна быть в границах (как у `index_of`).
- Предложение:
  - Решить в фазе 4 визуально: либо оставлять плашку зоны под зданием как «подложку» участка (тогда ничего менять не нужно), либо в `_update_cell` скрывать цвет зоны (`Color(0, 0, 0, 0)`), пока `grid.tile_type[i] == CityGrid.Tile.BUILDING`.
  - Над `get_zone` добавить комментарий `## Клетка должна быть в границах.` (по аналогии с `index_of`).

## Предложения по фазе 4

### 1. Модель спроса R/C/I для MVP (`scripts/simulation/demand.gd`)
В MVP у нас есть три понятных показателя из построенных зданий:
- `population: int` — сумма `population` всех жилых домов (`R`);
- `commercial_jobs: int` — сумма `jobs` всех коммерческих зданий (`C`);
- `industrial_jobs: int` — сумма `jobs` всех промышленных зданий (`I`);
- `total_jobs: int = commercial_jobs + industrial_jobs`.

Чтобы не было проблемы «курица или яйцо» в пустом городе и значения сразу подходили для полосок UI в фазе 5 (диапазон `[-1.0, +1.0]`, здания растут при `demand > 0.0`):
- **Жилой спрос (`R`):** люди заселяются, когда есть свободные рабочие места + небольшой стартовый буфер (`BASE_R = 20`):
  ```gdscript
  var target_pop: float = float(total_jobs) + 20.0
  demand_r = clampf((target_pop - float(population)) / 50.0, -1.0, 1.0)
  ```
- **Промышленный спрос (`I`):** заводы — базовый работодатель (~70% рабочих мест от населения) + стартовый буфер (`BASE_I = 15`):
  ```gdscript
  var target_ind: float = float(population) * 0.7 + 15.0
  demand_i = clampf((target_ind - float(industrial_jobs)) / 40.0, -1.0, 1.0)
  ```
- **Коммерческий спрос (`C`):** магазинам нужны жители-покупатели (~30% от населения, появляется после первых жителей):
  ```gdscript
  var target_com: float = float(population) * 0.3
  demand_c = clampf((target_com - float(commercial_jobs)) / 30.0, -1.0, 1.0)
  ```
**Как это работает в игре:** на старте (`pop = 0, jobs = 0`) есть спрос на `R` (`+0.4`) и `I` (`+0.38`), спрос на `C` равен `0.0`. Игрок размечает `R` и `I` → вырастают первые дома и заводы → появляется население → включается спрос на `C` → растут магазины → новые рабочие места снова поднимают спрос на `R`.

### 2. Выбор клеток для роста (`scripts/simulation/growth.gd`) и кэш
Между двумя вариантами из «Отложенных решений» (`ARCHITECTURE.md:123`) — **однозначно кэш пустых зонированных клеток (`zoned_empty_cells`) в `CityGrid`**, а не обход соседей `road_cells`:
- **Почему не обход от `road_cells`:** радиус доступа `ROAD_ACCESS_RANGE = 3` (ромб из 24 соседей вокруг каждой клетки дороги), а не только 4 соседние клетки. Обход от дорог потребует проверять десятки пересекающихся клеток и всё равно фильтровать их по наличию зоны.
- **Как устроить кэш в `CityGrid`:**
  - Хранить словарь по типам зон или один словарь `zoned_empty_cells: Dictionary[Vector2i, bool] = {}` (либо три словаря в `Dictionary[Zone, Dictionary]` для `RESIDENTIAL`, `COMMERCIAL`, `INDUSTRIAL`).
  - Клетка входит в кэш тогда и только тогда, когда `tile_type[i] == Tile.EMPTY and zone[i] != Zone.NONE`.
  - Обновляется централизованно в `CityGrid` всего в 4 методах: `set_zone`, `set_road`, `place_building`, `remove_building`.
- **Алгоритм тика в `growth.gd`:**
  1. Для каждой зоны (`R`, `C`, `I`), у которой `demand > 0.0`:
  2. Собираем из кэша этой зоны клетки с `grid.has_road_access(cell)` (обычно это десятки клеток, проверка занимает доли миллисекунды).
  3. Если список не пуст — выбираем 1 случайную клетку (`candidates.pick_random()`), определяем поворот к ближайшей дороге (`find_nearest_road_dir(cell)`), вызываем `grid.place_building(...)` и в конце тика шлём один `Events.cells_changed.emit(changed)`.

### 3. Что делать с домом при потере доступа к дороге или снятии зоны
1. **Снятие зоны (`DEZONE`):**
   - Оставить текущее правило `can_zone`: **снять зону можно только с пустой клетки (`Tile.EMPTY`)**. Если на клетке уже выросло здание (`Tile.BUILDING`), `DEZONE` его не трогает — чтобы убрать застройку, игрок сначала сносит здание инструментом `BULLDOZE` (`B`), а затем при желании снимает зону (`4`). Это избавляет код от состояния «дом стоит на `Zone.NONE`».
2. **Потеря доступа к дороге у построенного здания:**
   - **Не сносить здание мгновенно в `remove_road`** — иначе, если игрок поставил игру на паузу и снёс перекрёсток, чтобы переделать его, все дома вокруг тут же исчезнут.
   - Проверять доступ к дороге у `grid.buildings` **только на тиках `SimClock`**:
     - В `BuildingInstance` добавить `var no_road_ticks: int = 0`.
     - На каждом тике: если `grid.has_road_access(b.cell)` → `b.no_road_ticks = 0`; иначе `b.no_road_ticks += 1`.
     - Если `b.no_road_ticks >= 3` (здание простояло 3 тика без дороги) — здание покидается и сносится через `grid.remove_building(b.id)`, а зона под ним остаётся (и отображается тусклой), чтобы при возврате дороги участок мог застроиться снова.

## Что сделано хорошо (коротко)

- **Единый источник правил `can_zone`:** и `BuildTool._update_drag` (для фильтрации превью), и `CityGrid.set_zone` используют одну и ту же функцию `can_zone`, поэтому превью на 100% совпадает с результатом применения инструмента.
- **Чёткое разделение `BULLDOZE` и `DEZONE`:** снос (`B`) убирает инфраструктуру, не стирая разметку зон, а снятие зоны (`4`) очищает только разметку — классическая удобная схема из SimCity / Cities: Skylines.
- **Один `MultiMeshInstance3D` с `use_colors = true` для всех зон:** `ZoneVisualizer` создаёт сетку один раз в `_rebuild()` и при `cells_changed` меняет только цвета нужных инстансов через `set_instance_color`, вообще не пересоздавая геометрию и трансформы.
- **Аккуратная работа с вводом:** разделение старта протягивания (`_unhandled_input`) и завершения/отмены (`_input`) с прижатием курсора к границам карты (`clamp_to_bounds`) закрыло все крайние случаи с выходом мыши за карту и будущим UI.
